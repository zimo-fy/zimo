# ADR-0015：登录账号托管模型配置

状态：Accepted

日期：2026-09-09

## 2026-10-19 修订

模型标识、显示名称和 API 地址不再在代码中写死。登录只读取已经保存在系统中的托管模型配置并轮换 `modelApiKey`。没有这份配置时登录失败。

## 背景

模型地址与 API Key 原由用户在设置页手动填写。当前产品账号体系已经能在登录响应中返回 `modelApiKey`，并曾要求统一使用固定托管端点与模型标识。继续保留手动输入会造成配置重复、错误地址和凭据来源不清晰；后续已改为用户在引导或设置中自行保存 API 地址与模型标识，代码不再嵌入生产 URL 或默认模型名。

## 决策

- 认证 Adapter 将 `modelApiKey` 作为登录成功的必填字段，但认证 IPC 不暴露它；
- Main 在登录事务中调用模型配置服务，将 Key 放入 SecretStore，并写入固定 ID 的 Provider/Model 元数据；
- 固定模型自动成为默认，历史 Provider 只停用、不删除，以维持引用完整性；
- 生产设置页只读展示并允许连接测试，手动 mutation 由 Application 拒绝；
- 仅开发服务器模式允许设置页更新固定托管 Provider 的模型标识、HTTPS/loopback 地址和可选的新 API Key；Application 仍拒绝新增、删除、改名、能力变更、停用和非固定 Provider mutation；
- 开发页面不读取当前 Key。留空复用登录凭据，填写新 Key 时继续使用 SecretStore 的新引用写入、数据库失败补偿和旧引用清理流程；
- 模型配置失败即回滚登录，退出登录删除模型密钥并停用 Provider；
- 仅未打包开发环境允许通过环境变量把固定模型地址覆盖到 loopback 测试服务；设置页可编辑入口进一步要求开发服务器标记，不能由打包环境开启。

## 结果

用户登录后即可直接对话，生产 Renderer 不接触模型密钥。开发 Renderer 只在开发者主动替换 Key 时短暂持有新值，永远无法读取既有 Key。认证和模型配置形成同一成功/失败边界。代价是升级前会话需要重新登录一次，且当前不能添加其他模型；未来恢复多模型时应新增明确的账号策略和迁移，而不是把开发入口带入生产。

## 未选择

- 把 `modelApiKey` 返回 Renderer 后由页面保存：违反密钥边界；
- 将 Key 直接写入 SQLite 或 `.env`：无法满足秘密存储要求；
- 登录成功后异步、尽力配置模型：会留下无可用模型的半登录状态；
- 删除历史 Provider：可能破坏 Conversation 与 Agent 引用。
