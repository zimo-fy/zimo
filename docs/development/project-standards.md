# 项目工程规范

本文规定跨语言、跨进程和跨功能的工程约束。具体编码细节分别见 TypeScript、React、Electron/Node.js 与 Git 规范；冲突时按“安全与 ADR → 架构文档 → 本文 → 技术专项规范 → 功能文档”的顺序执行。

## 目录与架构

- 代码按业务能力和层次组织，不按“所有组件”“所有服务”建立全局杂物目录；目录名使用 kebab-case；
- 依赖方向固定为 Renderer → Preload → Main → Application → Domain ports，Adapter 实现 Domain ports；Domain 不反向依赖基础设施；
- 每个 package 通过 `exports` 或根 `index.ts` 提供最小公共 API；禁止跨包深层导入内部文件；
- 共享代码只有在两个以上稳定消费者且语义一致时提取；禁止提前建立万能 base class、通用 service 或无领域含义的 helper；
- 业务规则进入 Domain/Application，IO 和第三方 SDK 进入 Adapter，进程装配和环境读取只在 composition root；
- 新的跨层依赖、后台进程、远程能力、存储方式或安全边界必须先写 ADR。

## 功能开发顺序

1. 明确需求、非目标、权限边界和失败行为；
2. 先定义 Domain port、DTO/Schema 和错误语义，再实现 Application 用例；
3. Adapter 只实现端口，不向内层泄露 SDK、Electron、ORM 或文件系统类型；
4. 最后接入 Main/Preload/Renderer，并补齐用户可见的加载、空、错误、取消和成功状态；
5. 按风险补测试、文档和 `PROGRESS.md`，运行质量门禁。

不得用 UI 假状态掩盖未实现能力；未开放操作返回稳定错误并明确标注预览或不可用。

## 依赖与包管理

- 只使用根目录声明的 pnpm 版本和 lockfile；不得混用 npm、Yarn 或提交不同包管理器锁文件；
- 新依赖必须说明用途、维护状态、许可证、体积、运行进程及可替代方案；已有平台能力足够时不引入依赖；
- 生产依赖与开发依赖正确分类；Electron Main 运行时需要的原生模块必须验证目标系统和架构；
- 精确锁定影响运行时、安全边界、原生 ABI 或打包体积的核心依赖；升级应单独变更并附回归结果；
- 禁止直接修改 `node_modules`；补丁必须使用受版本控制的 patch 机制并注明退出计划；
- 删除代码后同时检查并移除不再使用的依赖、脚本、类型和打包资源。

## 配置、秘密与环境

- 配置应有类型、默认值、Schema 和所有权；环境变量只在应用入口读取并立即解析，业务代码不散落读取 `process.env`；
- 开发、测试、生产配置显式分离，不能以 hostname、用户名或文件是否存在推断环境；
- API Key、令牌、签名证书和用户秘密不得进入 Git、`.env`、命令行参数、URL、Renderer 状态、普通数据库或日志；
- 秘密只通过受控 UI 提交给 Main，并由 `SecretStore` 保存；测试使用明显无效的固定凭据；
- `.env.example` 只描述非秘密配置和占位符，不包含可工作的凭据。

## 数据与迁移

- 数据库访问只通过 Repository；UI、Domain 和 Application 不执行 SQL；
- Schema 变更必须提交顺序 migration，禁止编辑已经发布的 migration，禁止生产环境使用 schema push；
- migration 应可在空库、旧版本库和重复启动场景安全执行；失败必须回滚或进入明确不可继续状态；
- 写操作明确事务边界、唯一约束、并发顺序和幂等策略；时间统一保存为 UTC ISO-8601；
- 删除行为明确软删/硬删、引用约束、关联文件清理与恢复能力；涉及用户数据时默认保守；
- 不保存可由权威数据稳定推导的重复字段，确需缓存时说明失效和重建策略。

## 契约与兼容性

- IPC、持久化 JSON、导入文件和远程响应均视为不可信输入，必须在边界使用 strict Schema 校验；
- 输入限制字符串长度、数组数量、对象深度、文件大小、URL 协议和 ID 格式；默认拒绝未知字段；
- 输出同样校验并映射为产品 DTO，不直接返回 ORM、SDK、Error、Buffer 或 Electron event；
- 公共契约变更应保持向后兼容；破坏性变更必须有版本、迁移方案和调用方同步计划；
- 时间、分页、排序、空值和错误码语义必须明确，不能由不同调用方自行猜测。

## 安全与隐私

- 使用最小权限和默认拒绝；新增文件、网络、Tool、MCP、Shell、剪贴板、通知或外链能力必须列出威胁和确认点；
- 用户正文、文件正文、模型上下文、Tool 参数值/输出和认证信息不得进入普通日志或遥测；
- 文件操作必须解析真实路径、限制根目录、拒绝符号链接逃逸，并设置数量、大小、格式、解压规模和处理超时；
- 远程内容、Markdown、模型输出与 Tool 输出一律是不可信数据，不作为指令、HTML 或代码执行；
- 安全控制失败时关闭能力，不降级到明文存储、宽松 CSP、任意导航或跳过校验。

## UI、可访问性与国际化

- 复用 `@zimo/ui` 或 feature 级通用组件和设计 token，不在页面复制按钮、输入框、弹层和状态样式；
- 所有交互支持键盘，焦点清晰且顺序合理；图标按钮有 accessible name，错误与字段关联，状态不只依赖颜色；
- 弹层负责焦点进入、Escape、焦点归还和背景交互隔离；动态状态使用合适的 live region；
- 文案面向用户说明结果和下一步，不暴露堆栈、内部路径、供应商原始错误或伪造成功；
- 新页面考虑窄窗口、文本放大、长文案、空数据和 reduced-motion；中文标点与术语保持一致；
- 用户可见文案集中在明确区域，避免由字符串拼接形成难以国际化的句子。

## 性能与资源

- 优先测量后优化；PR 中说明新增的大依赖、模型、Worker、原生二进制和打包体积变化；
- Renderer 不执行大文件解析、Embedding、数据库查询或长时间 CPU 任务；重任务放到受控 Main Adapter/Worker；
- 列表和搜索设置合理上限、分页或虚拟化策略；输入触发查询应防抖并处理过期响应；
- 流、订阅、定时器、文件句柄、数据库事务和窗口事件必须在完成、取消或卸载时释放；
- 缓存必须有容量、生命周期、键规则和失效方式，不能以无界 Map 代替存储设计。

## 测试、文档与完成定义

- 修复缺陷先建立可复现测试；新业务规则优先单元测试，边界使用 contract/integration，关键旅程使用少量 E2E；
- 测试确定、隔离且离线；不使用任意 sleep、不依赖执行顺序、不连接真实账户或生产服务；
- 新功能同步需求/功能文档，架构决策同步 ADR，操作方式同步开发文档，阶段状态同步 `PROGRESS.md`；
- 注释说明原因、约束和风险；代码能表达的行为不写重复注释；TODO 必须带 issue 或日期和退出条件；
- 完成意味着实现、错误路径、权限边界、测试、文档、可访问性及适用门禁均已处理；“本机能运行”不等于完成。

## 代码评审清单

- 变更是否属于需求范围，是否混入无关重构；
- 分层和公共 API 是否正确，文件规模是否符合治理门槛；
- 外部输入、秘密、路径、权限、超时、取消和审计是否处理；
- 加载、空、失败、重试、禁用和并发状态是否可理解；
- 是否存在兼容性、migration、打包体积或跨平台风险；
- 测试是否覆盖行为而非实现细节，文档和进度是否与代码一致。
