# 会话问答卡批量展示与提交后残留

## 现象与影响

模型一次提交多个结构化问题时，页面在同一张卡中全部展示；卡片又被渲染在消息输入表单内部，导致输入框整体高度和结构发生变化。用户提交回答后，Renderer 只等待流事件清理状态，IPC 已成功时卡片仍可能短暂或持续残留。

这会让确认流程显得拥挤，也无法形成“回答一题，再进入下一题”的清晰节奏。残留卡片还可能让用户误以为提交失败并重复操作。

## 证据与根因

- `UserQuestionService` 原先把模型传入的 1–3 题原样放进一个 `PendingUserQuestion`，因此 Renderer 只能批量展示和批量回答。
- `ChatComposer` 原先把 `UserQuestionCard` 放在消息输入 `<form>` 内，卡片自然参与表单布局并撑高输入框。
- `useChatQuestions.answer` 在 `{ accepted: true }` 后没有删除本地问题，只依赖 `question.resolved`；任何事件丢失、时序变化或页面状态竞争都会留下旧卡。

## 修复

- Application 将一个模型问题批次保留在内存中，但每次只发布一题；当前题回答通过严格校验后，旧问题 ID 一次性失效并发布下一题，最后汇总全部答案返回原 Tool Call。
- 问答卡移到消息表单外，使用绝对定位浮在输入框上方，不改变输入框原有 DOM 和布局。
- IPC 返回接受成功时，Renderer 立即按问题 ID 移除当前卡；流事件继续承担跨窗口内刷新恢复与下一题同步。

## 回归覆盖

- Application 单元测试验证两题按顺序发布、问题 ID 更新、事件顺序以及最终答案汇总。
- Renderer Hook 测试验证 Main 接受回答后立即移除当前卡。
- 问答卡组件测试继续覆盖多选与自输入。

## 剩余风险

待用真实模型完成一次多题自主提问的应用内人工验证，重点检查窄窗口、长选项、提交后下一题切换和停止生成。
