# 自动化运行与删除后侧栏任务列表未同步

## 现象与证据

手动“立即运行”后的专用会话已有消息，但左侧任务列表不实时出现。原删除逻辑还会软删除专用会话；左侧若仍保留旧缓存，点击时出现“正在初始化新任务／没有找到该会话”。2026-10-12 本地日志显示手动与定时运行均完成；数据库中被删除自动化及对应会话的 `deleted_at` 同时写入。

## 根因

Application 一直复用自动化的专用会话，普通任务列表按会话消息数展示。Main 的调度运行未向 Renderer 通知会话列表变化；自动化页面的“立即运行”和“删除”只刷新本页，未刷新侧栏。因而已创建消息的会话不会即时出现，已删除会话也不会即时消失。点击陈旧条目后，`conversations.get` 正确返回 `CONVERSATION_NOT_FOUND`，但 ChatPage 将其当作初始化失败留在原页。

## 修复与边界

- 在专用会话的运行消息建立后、运行终态落库后和删除自动化配置后发出列表变化通知；手动与定时运行使用同一路径。
- Main 只广播严格空对象事件，不含账号、指令正文或会话数据；Preload 校验后仅暴露具名订阅，Renderer 收到后复用 `taskState.refresh()`。
- 若用户恰好点到已删除的旧条目，ChatPage 重新读取任务列表；当前选中项消失且无其他任务时回到草稿态，不再停留在不存在的会话。后续删除自动化时保留已有历史会话，见[独立问题记录](automation-delete-preserves-history.md)。
- 不改变一个自动化对应一个专用会话的存储方式，也不为每次运行新建任务。

## 验证与剩余风险

Application 测试覆盖手动/定时运行建立、完成及删除的通知时机；Contracts 测试拒绝事件额外字段，Preload 测试覆盖过滤与取消订阅。相关类型检查、单测、构建结果见 `PROGRESS.md`。真实应用内手动、定时触发和删除交互仍需人工复测。若 Renderer 窗口未打开，事件不会排队；下次打开时既有初始列表读取会恢复正确状态。
