# 手动会话压缩与用户记忆

## 范围与实施步骤

1. 在最新一条已完成的助手回复下提供“更多”菜单：复制回复、压缩当前会话；其他助手回复仅可复制。手动压缩没有聊天消息副作用，正式版保留最近 12 条完成消息；开发服务器为便于测试，手动压缩仅保留最近 2 条。历史不足时提示不可压缩。
2. 增加具名 IPC、Preload API 和 Application 手动压缩用例；复用版本化检查点和会话流事件。会话运行期间拒绝压缩，压缩期间拒绝新的会话运行；请求可取消、失败不覆盖上一个有效检查点。
3. 独立账号级 `user_memories` 表保存偏好、目标和未解决问题。用户可手动增删改及停用；普通会话使用 `save_user_memory` 结构化模型工具，由模型提出类别和内容，写入当前登录账号。压缩摘要仅负责当前会话交接，不包含长期记忆提取或保存逻辑。所有操作从 Main 的有效登录会话确定账号，不接受 Renderer 传入的所有者。
4. 设置页增加“用户偏好与记忆”区域，提供列表、创建、编辑、启用/停用和删除；说明启用的记忆会随模型请求发送到模型服务。
5. 每次普通会话模型请求前读取当前账号启用的记忆，以有界、低于本轮用户明确指令的历史上下文注入；创建空会话不发起模型请求，新会话首次发送时即生效。内容计入压缩 token 预算，压缩摘要不替代用户记忆。Workflow 内部节点暂不注入。
6. 补充边界、账号隔离、取消、重启、设置 UI、首轮请求与失败测试，运行格式、lint、类型、单元、集成、构建及适用 E2E，更新需求、实施计划、进度和数据/IPC 文档。

## 行为与边界

- 手动压缩使用用户当前会话可用模型，不执行 Tool。即使未达到自动水位也可压缩，但至少有一条可压缩的已完成消息。并发压缩与模型运行互斥，关闭窗口或退出账号时取消。
- 资格按当前会话、最新有效检查点之后的已完成非 system 消息计数：数量大于保留条数时才可手动压缩。开发服务器保留 2 条，因此通常完成两轮用户/助手对话（4 条消息）后可测试；正式版保留 12 条，需至少 13 条。这里不改变自动压缩的 1.2M token 预算、80%/90% 水位或其保留 12 条的策略。
- 记忆以 `externalUserId` 隔离；最多 100 条、单条 500 字符，模型上下文最多注入 20 条及 4,000 字符，优先偏好，再按更新时间。目标和问题可停用，不自动推断已经完成。
- 模型工具只在由桌面窗口发起、已登录且模型支持 Tool Calling 的普通会话自动暴露；微信入站、自动化后台运行、压缩请求和 Workflow 节点不自动暴露。一次调用只提交一条 `kind` 与 `content`，不接受账号 ID。Application 核对当前账号与本轮账号快照、限制 500 字符和 100 条总量，完全相同的启用/停用记忆不重复写入且不自动重新启用。首版不判断长期价值、原文出处、冲突或敏感类别；模型判断错误可能把不该跨会话保存的内容写入数据库，用户可在设置页删除或停用。
- 成功保存的记忆从下一次普通会话模型请求起生效，包括新会话首轮；本轮模型请求已编译过记忆上下文，不追溯修改。工具调用可能要求后续模型轮次完成最终回复，因此不保证一次用户指令仅有一次模型 HTTP 请求。Workflow 内部节点暂不注入。
- 修改或删除记忆后，下一轮请求立即生效；已发送给供应商的请求和旧会话记录不会追溯撤回。普通日志不得出现记忆正文，开发态敏感模型 payload 可能包含记忆，应按现有敏感日志策略处理。
- 记忆是用户提供的背景，不是系统权限或 Tool 授权；与本轮用户明确指令冲突时以后者为准。
